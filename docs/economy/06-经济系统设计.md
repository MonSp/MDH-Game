# 修仙世界市场经济引擎

> 《太古纪元：霸业》的经济不再是静态配置——矿石从矿工的镐下产出，流经铁匠的熔炉变成装备，再由商贾运往他乡坊市。每一次生产都在增加供给、每一次消费都在推高需求，物价随 NPC 的劳作与交易而自然波动。这里没有"系统刷钱"，每一枚灵石都有它的来处和去处。

---

> **架构说明**：本文档描述的经济系统已从 V1 的静态设计全面升级为 **NPC 行为驱动的动态市场引擎**。
>
> **V2**：商品池（CommodityPool）追踪六类大宗商品的供需，对数弹性定价引擎（PriceEngine）基于供需比计算实时市价，所有 NPC 生产/交易行为统一接入 MarketRegistry，家族库房自动抽税，商队跨区域套利平抑价差。详情见 [经济引擎 Spec](../.trae/specs/economy-market-engine/spec.md)。
>
> **V3（最新）**：NPC 个人物品系统全部迁移到 C++ 侧——`ItemSlot{itemId,count}` 堆叠结构替代了旧的松散 `Item` 结构，16 种生产行为同时写入 NPC 个人背包和 CommodityPool，WASM 新增 `ecs_getNPCItems` 按需拉取接口，TS 端不再独立维护 NPC 物品数据。新增 `ItemRegistry.h` 统一管理 15 种物品 ID、名称和基准价值。详情见 [NPC 物品系统 Spec](../.trae/specs/npc-inventory-cpp/spec.md)。同时完成了 [评审迭代修复](../.trae/specs/economy-review-fixes/spec.md)：统一税收基准、前端买卖回写 WASM、Cook 盈利修正、EconomicSignals 缓存优化等 8 项改进。

## 一、经济全貌——灵石从哪里来，到哪里去？

### 1.1 五层经济循环

```
┌─────────────────────────────────────────────────────────────┐
│                   ① 资源层（NPC 生产行为）                      │
│  采矿→矿石  耕种→食物  伐木→材料  锻造→装备  炼丹→丹药          │
│  16 种生产行为每日向 CommodityPool 注入数百万单位商品            │
├─────────────────────────────────────────────────────────────┤
│                   ② 商品池（CommodityPool）                    │
│  按家族/区域追踪六类商品的 supply 与 demand                     │
│  Ore | Food | Equipment | Materials | Pills | SpiritStones   │
├─────────────────────────────────────────────────────────────┤
│                   ③ 定价层（PriceEngine）                      │
│  price = basePrice × (1 + 0.3 × ln(demand / supply))         │
│  供不应求涨价，供过于求跌价，价格限幅 [0.3×base, 3.0×base]        │
├─────────────────────────────────────────────────────────────┤
│                   ④ 流通层（Trade + Treasury + Caravan）       │
│  家族库房自动抽税 5% → 资助弟子突破 → 商队跨区套利平抑物价       │
├─────────────────────────────────────────────────────────────┤
│                   ⑤ 反馈层（EconomicSignals → NPC 行为）       │
│  矿石紧缺 → 矿工系 NPC 采矿概率 ×1.5 → 供给增加 → 价格回落       │
└─────────────────────────────────────────────────────────────┘
```

> **一句话理解**：矿工挖出矿石 → 矿石池供给增加 → 矿石降价 → 铁匠买矿石更便宜 → 铁匠锻造更多装备 → 装备池供给增加 → 装备降价 → 商贾低价买入装备 → 运往高价区卖出 → 利润进家族库房 → 库房资助弟子突破 → 突破消耗灵石 → 灵石需求增加 → 商贾更积极买卖……

### 1.2 与传统经济系统的区别

| 维度 | 传统游戏经济 | 本系统 |
|:---|:---|:---|
| **货币发行** | 系统无限刷钱 | 零发行——所有灵石来自 NPC 生产行为 |
| **物价** | 策划手工配置 | 供需比实时计算，NPC 行为自动调节 |
| **NPC 角色** | 静态商店，价格固定 | NPC 是生产者+消费者+交易者，塑造市场 |
| **跨区交易** | 不存在或固定脚本 | 商队自动发现价差并套利 |
| **家族经济** | 纯剧情概念 | 家族库房自动抽税，资助弟子，有借有还 |
| **NPC 物品** | 货币抽象化，NPC 不持有实物 | 每个 NPC 拥有独立背包（ItemSlot 堆叠），采矿→矿石入包，锻造→消耗矿石产出装备 |
| **数据权威** | TS 与 C++ 各维护一套 | C++ 为唯一数据源，TS 通过 WASM 按需拉取 |

## 二、商品池——区域经济的基本单元

### 2.1 六类大宗商品

每个家族/宗门拥有一份 CommodityPool，追踪该区域六类商品的供给量（supply）和需求量（demand）：

| 商品 | basePrice | 来源行为 | 消耗行为 |
|:---|:---|:---|:---|
| **矿石 Ore** | 5 灵石 | Mine（采矿） | Craft（锻造）、Refine（精炼）、Construct（大型建造） |
| **食物 Food** | 3 灵石 | Farm（耕种）、Fish（捕鱼）、Cook（烹饪）、Hunt（狩猎） | Eat（进食）、Cook（烹饪加工） |
| **装备 Equipment** | 40 灵石 | Craft、Tailor（裁缝）、Construct、Build（建造） | —（耐久消耗未来扩展） |
| **材料 Materials** | 4 灵石 | Lumber（伐木）、Gather（采集）、Refine（精炼） | Craft、Build、Construct、Repair（修理） |
| **丹药 Pills** | 80 灵石 | Alchemy（炼丹） | Breakthrough（突破）、Heal（疗伤） |
| **灵石 SpiritStones** | 1 灵石 | Sell（出售）、Bargain（议价）、Trade（交易） | Buy（购买）、Breakthrough（突破） |

> 灵石既是流通货币也是商品。它的供需同样受市场调节——开采矿石转化为灵石（通过出售），突破/战争消耗灵石。供过于求时灵石购买力下降（通胀），供不应求时灵石更值钱（通缩）。

### 2.2 商品池数据结构

```cpp
struct CommodityPool {
    int64_t supply[6];   // 各商品供给量（初始 100，避免除零）
    int64_t demand[6];   // 各商品需求量（初始 0，自然衰减）
};
```

**关键设计**：
- **供给是库存**：NPC 生产增加 supply，永远是正值
- **需求是流量**：NPC 消费增加 demand，每 600 帧自动衰减 ×0.95，模拟需求自然消退
- 供需分离确保价格不会因一次性的短暂消费而永久扭曲

### 2.3 NPC 个人物品存储——ItemSlot 堆叠系统

V3 中每个 NPC 拥有独立的物品背包，存储在 `ResourcesComponent` 中。物品使用紧凑的 `ItemSlot` 堆叠结构：

```cpp
struct ItemSlot {
    uint32_t itemId;   // 物品 ID（见 ItemRegistry）
    int32_t count;     // 堆叠数量
};

struct ResourcesComponent {
    int64_t spiritStones;         // 灵石余额
    std::vector<ItemSlot> items;  // 物品背包（按 itemId 堆叠）
    uint32_t equipmentItemId;     // 当前装备物品 ID（0=无装备）
    int32_t familyContribution;   // 家族贡献值
    // ...
};
```

**设计要点**：
- **堆叠而非散列**：同一种物品（如 15 矿石）只占一个 `ItemSlot`，而非 15 条记录。`vector` 在 NPC 通常持有 0-5 种物品时比 map 内存效率高得多
- **材料守卫**：Craft/Refine/Cook 等消耗型行为在扣除材料前先调用 `hasItem(itemId, count)`，材料不足时行为自动拒绝
- **双写机制**：生产行为同时更新 NPC 个人 items（微观所有权）和 CommodityPool（宏观供需），两者独立但一致

## 三、定价引擎——对数弹性公式

### 3.1 定价公式

```
price = basePrice × (1 + elasticity × ln(demand / max(supply, 1)))
       clamped to [basePrice × 0.3, basePrice × 3.0]
```

| 参数 | 值 | 作用 |
|:---|:---|:---|
| elasticity | 0.3 | 价格对供需比的敏感度。值越小，价格越稳定 |
| floor | basePrice × 0.3 | 防止价格崩盘（供给再过剩，价格不会跌破 30%） |
| ceiling | basePrice × 3.0 | 防止恶性通胀（需求再大，价格不会超过 3 倍） |

### 3.2 定价示例

| 场景 | supply | demand | d/s | 价格 | 说明 |
|:---|:---|:---|:---|:---|:---|
| 均衡 | 100 | 100 | 1.0 | 5.0 | 供需平衡，基准价 |
| 供不应求 | 100 | 500 | 5.0 | **7.4** | 铁匠抢矿，矿石涨价 48% |
| 供过于求 | 1000 | 200 | 0.2 | **2.6** | 矿工太多，矿石跌到半价 |
| 极端紧缺 | 10 | 1000 | 100 | **15.0** | 触及天花板 3×base |
| 极端过剩 | 10000 | 1 | 0.0001 | **1.5** | 触及地板 0.3×base |

### 3.3 为什么用对数而非线性？

```
线性:    price = base × (1 + 0.3 × d/s)     — 供给翻倍，价格翻倍，过于剧烈
对数:    price = base × (1 + 0.3 × ln(d/s)) — 供给翻倍，价格变化平缓

示例（Ore base=5, supply=100）:
demand=200 → 线性: 5×1.6=8.0  对数: 5×1.208=6.0
demand=500 → 线性: 5×2.5=12.5 对数: 5×1.483=7.4
demand=1000→ 线性: 5×4.0=20.0 对数: 5×1.691=8.5 (受 ceiling 限制=15.0)
```

对数公式对初期供需变化敏感（小市场容易调节），对极端供需有自然阻尼（大市场不易剧烈震荡）。

## 四、NPC 生产行为——16 种行为的经济映射

### 4.1 行为→商品映射表

每个 NPC 执行生产/交易行为时，通过 `MarketRegistry::recordProduction()` / `recordConsumption()` 将产出/消耗同时写入**族级 CommodityPool**（宏观供需）和 **NPC 个人背包**（微观所有权）：

| 行为 | 消耗材料 | 消耗量 | 产出物品 | 产出量 | 个人背包变化 |
|:---|:---|:---|:---|:---|:---|
| **Mine** 采矿 | — | — | Ore | 15/次 | +15 矿石 |
| **Farm** 耕种 | — | — | Food | 30-60/次 | +30~60 食物 |
| **Fish** 捕鱼 | — | — | Food | 10/次 | +10 食物 |
| **Lumber** 伐木 | — | — | Materials | 8/次 | +8 材料 |
| **Gather** 采集 | — | — | Materials | 5/次 | +5 材料 |
| **Craft** 锻造 | Ore | 5 | Equipment | 1（70%概率） | −5 矿石, +0~1 装备 |
| **Refine** 精炼 | Ore | 8 | Materials | 2（50%概率） | −8 矿石, +0~2 材料 |
| **Cook** 烹饪 | Food | 2 | Food | 2-3（加工增益） | −2 Food, +2~3 食物 |
| **Tailor** 裁缝 | Materials | 3 | Equipment | 1（65%概率） | −3 材料, +0~1 装备 |
| **Alchemy** 炼丹 | — | — | Pills | 1（60%概率） | +0~1 丹药 |
| **Build** 建造 | Materials | 5/帧 | — | — | −5 材料/帧 |
| **Construct** 大型建造 | Materials+Ore | 各6/帧 | — | — | −6 材料, −6 矿石/帧 |
| **Repair** 修理 | Materials | 2/帧 | — | — | −2 材料/帧 |
| **Sell** 出售 | Equipment | 1 | SpiritStones | 10-50/次 | −1 装备 |
| **Buy** 购买 | SpiritStones | 10-100/次 | Equipment | 1 | −灵石, +1 装备 |
| **Bargain** 议价 | SpiritStones | base×0.7 | SpiritStones | base×(0.6~1.5) | 灵石差价 |
| **Trade** 交易 | Equipment | 1 | SpiritStones | 10-50/次 | 卖方 −1 装备 |

### 4.2 双写机制：NPC 背包 × CommodityPool

每到一次生产行为完成，系统执行**两条写入路径**：

1. **NPC 个人背包**：`resources->addItem(itemId, count)` 或 `resources->removeItem(itemId, count)`，物品实际所有权变更
2. **族级 CommodityPool**：`MarketRegistry::recordProduction/Consumption(entityId, type, amount)`，区域供需统计数据更新

```
Mine 完成 → addItem(ORE, 15)          ← NPC 背包：矿石 +15
          → recordProduction(Ore, 15)  ← CommodityPool：Ore supply +15
          → spiritStones += 15 × OrePrice ← NPC 灵石收益

Craft 完成 → hasItem(ORE, 5) ✓        ← 检查是否有 5 矿石
           → removeItem(ORE, 5)        ← NPC 背包：矿石 −5
           → recordConsumption(Ore, 5) ← CommodityPool：Ore demand +5
           → addItem(EQUIPMENT, 1)     ← NPC 背包：装备 +1
           → recordProduction(Equipment, 1) ← CommodityPool：Equipment supply +1
```

**材料不足时行为自动拒绝**：在扣除材料前，`hasItem(itemId, requiredCount)` 检查 NPC 背包。若不足，行为切换到 Rest 并记录反思负分。

### 4.3 关键改变：收益不再固定

V1 中 NPC 收益是硬编码的固定值（如采矿 +15 灵石/小时），现在改为：

```
NPC 收益 = 产出量 × 当前商品市价
```

这意味着同一个矿工，在矿石紧缺时（OrePrice=7.4）收益为 111 灵石/次，在矿石过剩时（OrePrice=2.6）收益只有 39 灵石/次。NPC 的反思系统会根据收益自动调整行为倾向——低收益时反思惩罚，高收益时偏好加强。

## 五、家族库房——从 NPC 交易到集体财富

### 5.1 自动抽税

每次 NPC 完成 Sell/Buy/Bargain/Trade 交易时，系统自动抽取 **5% 交易税**汇入家族 Treasury：

```
NPC 卖出装备获得 40 灵石
  → 家族 Treasury += 2 灵石（5% 税）
  → NPC familyContribution += 4（税额 × 2，贡献值双倍于税额）
```

### 5.2 库房资助突破

当核心弟子修为满值但个人灵石不足支付突破费用时，系统自动从家族 Treasury 借款：

| 境界突破 | 灵石消耗 | 说明 |
|:---|:---|:---|
| 练气 → 筑基 | 300 | 需一枚筑基丹的材料成本 |
| 筑基 → 金丹 | 1,000 | 大量丹药和灵石辅助 |
| 金丹 → 元婴 | 3,000 | 需顶级灵石布阵 |
| 元婴 → 化神 | 10,000 | 几乎耗尽一个小家族的积累 |

突破成功后弟子实力大增，可为家族创造更多价值（更好的生产/战斗能力）。突破失败则损失灵石但保留修为。

> 若家族 Treasury 不足，弟子无法突破，必须等待库房积累或自行攒钱。这产生了"穷家族弟子卡瓶颈"的涌现叙事。

### 5.3 家族贡献值

`familyContribution` 是每个 NPC 对家族的贡献积分。纳税时增加，借款突破时减少（可变为负值表示负债）。

未来扩展方向：
- 贡献值可兑换家族专属资源
- 高贡献者在长老会中有更大话语权
- 贡献值为负的弟子被家族催债

## 六、商队套利——跨区域物价平衡器

### 6.1 商队触发条件

当家主（FamilyHead）或长老（Elder）NPC 且家族有 **Merchant（商贾）** 传承时，在 Daily 层有 10% 概率触发商队行为。

### 6.2 套利逻辑

```
① CaravanSystem::findBestRoute(clanId)
   遍历所有家族的 CommodityPool，对 6 种商品逐一比较价差
   找出利润率最高的路线（价差 > 20% 且未在冷却中）

② 执行套利
   从低价区买入 100 单位商品 → 从 high-demand 区卖出
   利润 = 100 × (卖出价 - 买入价) × 0.95（5% 税后）

③ 物价平抑
   低价区：supply 减少 100 → 价格微涨
   高价区：supply 增加 100 → 价格微降
   多次往返后两区域价格趋于一致
```

### 6.3 商队风险与冷却

- **同路线冷却**：500 帧内同一路线不会再次触发，防止高频套利
- **劫匪风险**：5% 概率遭遇劫匪，损失 50% 货物
- **利润归属**：全部商队利润存入家族 Treasury

## 七、经济信号反馈——NPC 感知市场

### 7.1 EconomicSignals 数据源与缓存

V7.3 已将 EconomicSignals 从基于家族传承的启发式代理切换为读取真实供需数据。V3 进一步优化：`MarketRegistry` 层级维护 `CachedEconSignals` 缓存（TTL=100 帧），避免每个 NPC 每帧重复计算。需求衰减时自动标记缓存为 dirty。

```cpp
struct CachedEconSignals {
    float ironOreDemand, spiritStoneInflation, foodDemand;
    float equipmentDemand, materialDemand, cultivationDemand;
    uint64_t cachedFrame;
    bool dirty;
};
```

调用链路：

```
evaluateDaily()
  → MarketRegistry::getEconomicSignals(clanId, currentFrame)
      → 命中缓存（未 dirty 且帧差 < 100）→ 直接返回
      → 未命中 → 从 CommodityPool 计算供需比 → 写入缓存 → 返回
  → MarketRegistry::tickDecay(currentFrame)
      → 每 600 帧衰减 demand × 0.95，同时标记所有缓存 dirty
```

### 7.2 反馈回路

```
矿石紧缺（demand/supply = 3.0）
  → economicBiasFor(Mine) = 1.5 倍
  → 矿工系 NPC 采矿概率 ×1.5
  → 更多 NPC 选择采矿
  → Ore supply 增加
  → 矿石价格回落
  → 信号减弱，达到新均衡
```

这是一条完整的**负反馈闭环**——不需要策划手动调参，市场自动调节。

## 八、技术架构——如何让经济不卡

### 8.1 系统架构


### 8.2 性能特点

| 指标 | 数值 |
|:---|:---|
| CommodityPool 内存 | < 256 bytes / 家族（6×2 int64_t + map overhead） |
| NPC 个人背包内存 | 平均 < 80 bytes / NPC（假设 3 种物品，ItemSlot=8 bytes） |
| PriceEngine::getPrice | O(1) 纯算术，无循环 |
| 需求衰减 | 每 600 帧触发一次，O(families × 6) |
| EconomicSignals 缓存 | TTL=100 帧，命中率 > 99%（同帧内同族 NPC 共享） |
| CaravanSystem::findBestRoute | O(families × 6)，在 10% 触发概率下极少调用 |
| 生产行为接入 | recordProduction/Consumption 为 O(1) map 查找，addItem 线性搜索 ≤5 个元素 |
| WASM 物品导出 | 全量 NPCState 120 字节/NPC（itemCount + equipmentItemId 仅 2 字节），详情按需拉取 |

## 九、与 NPC 行为系统的对接

经济引擎通过三个接口与 NPC 行为系统深度耦合：

### 9.1 上行（NPC → 经济）

所有生产/交易行为通过 `MarketRegistry::recordProduction/Consumption` 写入 CommodityPool，同时通过 `ResourcesComponent::addItem/removeItem` 更新 NPC 个人背包。

### 9.2 下行（经济 → NPC）

`MarketRegistry::getEconomicSignals(clanId, frame)` 读取 CommodityPool 供需比，缓存命中则直接返回。`chooseByRole` 中的 `economicBiasFor` 函数根据行为产出的商品类型匹配对应的需求信号，调节行为选择概率。

```
经济紧缺 → 信号偏置 → NPC 行为调整 → 供需变化 → 经济缓解
```

### 9.3 WASM 桥接（NPC 背包 → 前端）

V3 新增两级导出机制：

- **全量同步**（每帧 `ecs_getNPCStates`）：`NPCStateWasm` 携带 `itemCount`（uint8_t）和 `equipmentItemId`（uint8_t），仅增加 2 字节
- **按需拉取**（前端打开面板时 `wasmGetNPCItems`）：返回完整物品列表（itemId + count） + spiritStones + familyContribution

```cpp
// 140 字节紧凑结构，itemCount/equipmentItemId 复用原有 _pad 空间
struct NPCStateWasm {
    // ...
    uint8_t commandStatus;      // offset 132
    uint8_t itemCount;          // offset 133 — NPC 背包物品种类数
    uint8_t equipmentItemId;    // offset 134 — 当前装备物品 ID
    uint8_t _pad;               // offset 135
    uint32_t squadId;           // offset 136
};
```

## 十、数字一览

| 指标 | V1（静态） | V2（市场引擎） | V3（物品系统） |
|:---|:---|:---|:---|

| 突破消耗 | 无 | **300/1000/3000/10000 灵石** | 不变 |
| 经济反馈 | 无 | **EconomicSignals 真实供需 → NPC 行为偏置** | **缓存优化（TTL=100, 命中率 >99%）** |
| 前端物价 | 静态随机波动 | **WASM 实时价格 → MarketPanel** | 不变 + 玩家买卖回写 CommodityPool |
| C++ 新增文件 | — | **5 个**（CP/PE/MR/CS/WASM 导出） | **+1（ItemRegistry）** |
| TS 新增文件 | — | **1 个**（MarketService） | 无新增（重构 NPCService） |
| 数据权威 | TS 与 C++ 各一套 | 部分统一 | **C++ 唯一数据源，TS 只读** |
